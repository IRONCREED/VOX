## 1. Канонические источники

### ICW-S01. Статус файла

Один Git-коммит образует каноническое состояние. Каждый файл имеет один
статус:

- `source` — непосредственно редактируемый источник;
- `generated` — воспроизводимое производное представление;
- `fixture` — устойчивый пример или ожидаемый результат;
- `external` — сторонний материал с указанным происхождением;
- `report` — доказательство проверки или выпуска.

Статус определяется путём и реестром. `app`, `src`, `content/config`, `public`,
`governance`, `semantic-core/corpus`, `semantic-core/materials`, схемы,
инструменты и тесты содержат источники. `dist`, `.next`, `semantic-core/dist`,
результаты покрытия и временные индексы содержат производные данные. Сохранённая в Git
release-проекция остаётся `generated`; ручное изменение запрещено.

### ICW-S02. Содержание

Материалы хранятся пакетами под `/semantic-core/materials/<material-key>/`. Один
пакет содержит `material.yaml`, `content.uk.md`, `content.en.md`, `intake.yaml`,
редакционные доказательства и локальные активы. Метаданные и сущности проходят
JSON Schema и графовую проверку до создания маршрута.

Минимальные поля материала:

| Поле | Назначение |
| --- | --- |
| `id` | Устойчивый `material.*` ID материала |
| `localizedContentIds` | Устойчивые ID локализованных редакций сайта |
| `translationKey` | Связь языковых редакций одного материала |
| `slug.uk`, `slug.en` | Полные локализованные маршруты |
| `title`, `summary` | Двуязычные публичные заголовок и описание |
| `authors` | Непустой список авторов, их ролей и необязательных проверенных URL профиля |
| `tags` | Устойчивые ID тематических связей, разрешимые в двуязычный реестр |
| `publication` | Редакция, даты, прежние URL и внешняя публикация |
| `status` | `draft`, `review`, `published` либо `deprecated` |
| `publishedAt` | Дата первоначальной публикации |
| `updatedAt` | Дата содержательного обновления |
| `featured` | Признак выделения в каталоге |
| `conversationViewId` | ID графового представления разговора |
| `entryQuestionIds` | Список входных независимых вопросов |
| `ageRestriction` | Обязательный рейтинг `0+`, `16+` или `21+` и необязательное двуязычное предупреждение о содержании |
| `site` | Локализованные подписи, категория, hints и параметры сайта |

Связанный полный материал использует необязательную секцию `publication`:

| Поле | Назначение |
| --- | --- |
| `provider` | Значение `zenodo` |
| `recordId` | Устойчивый числовой ID опубликованной записи |
| `title` | Точное публичное название связанной публикации |
| `doi` | Постоянный concept DOI публикации; version-specific record ID хранится отдельно |
| `pdfFile` | Предпочтительный ключ PDF-файла внутри записи |

Вопросы, понятия, утверждения, протоколы, источники, активы, отношения и
представления хранятся независимыми реестрами `/semantic-core/corpus`.
Каждый вопрос имеет `standalone: true`, понятен вне контекста родительского узла
и не содержит `parentId`, `children`, `depth` или `materialId`; порядок
принадлежит `view`. Компонент страницы не содержит копию материала, перевода,
графа или подготовленного ответа.

Общие двуязычные страницы хранятся в реестре
`/semantic-core/corpus/pages/registry.json`. Запись страницы имеет stable ID,
тип, локализованные slug, заголовок, краткую подпись, описание, eyebrow и тело;
необязательный `conversationViewId` связывает страницу с уже опубликованным
публичным `view`. Политики и индекс корпуса являются страницами, а не текстом,
захардкоженным в навигации.

### ICW-S03. Локали и маршруты

Реестр локалей учреждает `uk` и `en`; `uk` является значением по умолчанию.
Каждая публичная страница имеет явный языковой маршрут. Корневой `/` выполняет
устойчивое перенаправление на `/uk/` либо отдаёт украинскую страницу с
`x-default`, если платформа требует иной формы.

Связь переводов устанавливается `translationKey`, а не совпадением пути или
заголовка. Отсутствующий перевод не создаёт ложную альтернативную ссылку.
Localized slug способен отличаться между локалями.

### ICW-S04. Переходный прототип

До переноса содержания существующие `app/page.tsx` и `app/globals.css`
сохраняются как источник визуального и поведенческого прототипа. Переход
переносит подтверждённые свойства в новую систему и удаляет старый источник
только после проверки маршрутов, визуального результата и сборки.

### ICW-S05. Жизненный цикл и редакционная граница

Добавление, обновление, снятие с публикации, исключительное физическое удаление,
версии и пересборка регулируются
[`CONTENT_LIFECYCLE_2026-08-11.md`](CONTENT_LIFECYCLE_2026-08-11.md).

Создание пакета материала, авторского текста, `view`, графовых рёбер и
редакционных оснований является ручной работой. `corpus:scan` обнаруживает
кандидатов, `corpus:apply` применяет только явно разрешённые решения по
сущностям, а `corpus:build` создаёт проекции и индекс. Ни одна из этих команд не
учреждает содержательную связь и не принимает материал за редактора.

Публичная проекция включает только сочетание `status: published` и
`visibility: public`. Статусы `draft`, `review` и `deprecated` исключаются из
маршрутов, индекса и публичного Knowledge-пакета. Ранее опубликованный источник
снимается через `deprecated` и сохраняется; его физическое удаление проходит
как защищённое действие.

### ICW-S06. Серия материалов

Повторяемая редакционная группа публикаций называется `серией материалов`
(`material series`). Каноническая запись `series.*` хранится в
`/semantic-core/corpus/series/registry.json` и объявляет двуязычные slug,
заголовок, описание, категорию, теги, даты и упорядоченный список `materialIds`.
Каждый входящий материал хранит только `seriesId` и однозначную позицию; порядок
не выводится из даты, имени каталога или номера в заголовке.

Публичный каталог сворачивает части опубликованной серии в одну запись. Она
сортируется по `updatedAt` серии, показывает устойчивую идентичность серии и
сведения о её последней части и ведёт на `/uk|en/series/{slug}`. Отдельная
страница серии получает обычные карточки всех частей в каноническом порядке.
Маршруты самих материалов сохраняются, а их страницы получают ссылку на серию
и переходы к предыдущей и следующей части.

Добавление части обновляет запись серии, её `revision`, `updatedAt`, список
материалов, проекции и индекс. Оно не создаёт отдельную строку этой части на
главной или в категории. `series` не владеет вопросами: вопросы остаются
самостоятельными сущностями, а каждый материал сохраняет собственный `view`.

## 2. Технологический профиль

### ICW-T01. Языки и представления

Проект использует:

- TypeScript и TSX для прикладной логики, маршрутов и React-компонентов;
- CSS для визуального представления;
- Markdown для локализованного содержания и нормативных документов;
- JSON-совместимый YAML и JSON для метаданных, реестров и схем семантического ядра;
- JSON для манифестов, схем и данных конфигурации;
- JavaScript или MJS только для конфигурации и границы инструмента, которая
  требует этот формат;
- Bash только для закреплённых сценариев жизненного цикла Sites.

HTML создаётся серверным рендерингом React и проверенного Markdown. Встраиваемый HTML содержания
проходит разрешающий список и очистку. SQL, база данных и серверное изменяемое
состояние появляются после отдельного акта.

Назначение языка определяет правила проверки. Markdown является каноническим
текстовым представлением статьи; YAML/JSON семантического ядра является канонической
структурой сущностей, хотя эти форматы не исполняют роль прикладного языка.

### ICW-T02. Среда и зависимости

Текущая среда использует Node.js линии, объявленной в `package.json`, npm и
единственный `package-lock.json`. Точное дерево зависимостей задаётся lockfile.
ECMAScript modules являются форматом программных модулей.

TypeScript сохраняет `strict`, `noEmit`, `isolatedModules`,
`forceConsistentCasingInFileNames` и совместимость с маршрутизатором. Во время
первого инженерного этапа дополнительно рассматриваются
`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`,
`useUnknownInCatchVariables` и `noFallthroughCasesInSwitch`; каждое несовместимое
значение получает записанное основание.

Vinext и Sites образуют границу исполнения. Прикладные модули не импортируют
внутренние детали платформы, когда тот же контракт выражается стандартным API
Next/React либо локальным портом.

### ICW-T03. Внешние данные

Редакционный intake, параметры маршрута, query, URL подсказки, HTML, ответы API,
переменные среды и данные браузера являются внешним вводом. Граница чтения
создаёт `unknown`, проверяет схему и затем формирует внутреннюю модель.

Ответ Zenodo Records API проходит проверку origin, ID записи, структуры файлов,
ключа PDF, размера и публичной ссылки. Клиент принимает только HTTPS-адрес
`zenodo.org`, объявленный PDF и файловую границу `/api/records/`. Токен доступа
для опубликованных записей отсутствует.

Публичный аудиореестр является проверяемым вводом: активная дорожка обязана
разрешаться по устойчивому ID, иметь публичную HTTPS-страницу происхождения и
хотя бы один same-origin путь с объявленным MIME-типом. Клиент загружает медиа
только после явного пользовательского действия, не принимает произвольный URL
из query или DOM и не хранит ключ доступа. Отказ локального ресурса остаётся
состоянием управления и не влияет на серверное содержание. Runtime-запрос к
стороннему CDN не используется вместо публикуемого проверяемого файла.

Произвольный внешний HTML не передаётся React через `dangerouslySetInnerHTML`.
Разрешённый HTML проходит очистку, ограничение элементов, атрибутов, URL-схем и
источника. Ошибка проверки создаёт безопасную диагностируемую замену и не
оставляет частично доверенное состояние.

### ICW-A02. Направление зависимостей

Модель материала, локали, подсказки и графа компаньона не зависит от React,
файловой системы или Sites. Прикладной сценарий зависит от контрактов
репозитория. Адаптер семантического ядра читает только проверенную release-проекцию;
остальные адаптеры читают интерфейсную конфигурацию или URL и создают
проверенные модели. Шаблоны страниц получают готовые модели и компонуют
интерфейс.

`app` является корнем композиции и маршрутизации. Он способен импортировать
публичные границы модулей и не содержит бизнес-правила каталога,
локализации, подсказок или диалога.

Циклы между модулями запрещены. Компонент не импортирует приватный файл другого
модуля. Общий элемент переносится в `interface-system` только после появления
двух реальных потребителей и устойчивого общего контракта.

## 4. Имена и форматирование

### ICW-F01. Общий формат

Текстовые файлы используют UTF-8, LF и завершающий перевод строки. Хвостовые
пробелы запрещены. Автоматический форматтер управляет TypeScript, TSX,
JavaScript, CSS, JSON и поддерживаемыми конфигурациями.

Prettier получает:

| Параметр | Значение |
| --- | --- |
| `printWidth` | `100` |
| `tabWidth` | `2` |
| `useTabs` | `true` |
| `semi` | `true` |
| `singleQuote` | `true` |
| `trailingComma` | `all` |
| `arrowParens` | `always` |
| `bracketSpacing` | `true` |
| `endOfLine` | `lf` |

Канонический Markdown сохраняет авторское деление смысловых абзацев.
Автоматический перенос прозы по ширине строки отключается.

### ICW-F02. Имена

Каталоги и программные файлы используют `kebab-case`; React-компоненты и типы
используют `PascalCase`; функции и значения используют `camelCase`; константы
конфигурации верхнего уровня используют `UPPER_SNAKE_CASE`. CSS-селектор
использует `kebab-case` и называет компонент, роль или состояние.

Состояние получает форму `.is-expanded`, `.is-loading` либо аналогичное
утверждение. Единая система имён сохраняется внутри одного компонента. BEM не
является обязательным.

Функция называет действие и предмет: `loadLocalizedArticle`,
`resolveHintTarget`, `buildAlternateLinks`. Тип называет сущность:
`LocalizedArticle`, `HintSource`, `CompanionScenario`.

### ICW-F03. Строфическая организация

Пустая строка разделяет локальные фазы операции: получение, проверку,
преобразование, внешний эффект и формирование результата. Однотипные действия
сохраняют параллельную форму. Комментарий объясняет основание решения,
контракт, риск либо исключение.

Семантическое единство строфы, достаточность имени и уместность комментария
проверяются человеком. Prettier определяет локальную синтаксическую форму.

## 5. CSS и движение

### ICW-CSS01. Область стилей

`app/globals.css` содержит токены, reset, базовую типографику, общую тему
скроллбаров и действительно глобальные правила. Стиль компонента размещается в
CSS Module рядом с компонентом либо в явно названном файле
`interface-system`.

CSS custom properties являются источником цветов, размеров, слоёв, времени
движения и контрольных ширин. Повторяемое значение получает токен после
подтверждения общей семантики.

### ICW-CSS02. Выбор раскладки

CSS Grid применяется для двухмерного отношения строк и колонок:

- основной трёхколоночной оболочки;
- композиции, в которой выравнивание по обеим осям образует контракт;
- сложного графического модуля, где ячейки выражают структуру.

Flexbox применяется для одномерной последовательности. Обычный поток документа
используется для текста и вертикального списка материалов. Центрирование
единственного дочернего элемента относится к одномерному выравниванию и
использует Flexbox. Пара «значок + подпись», ряд переключателей, кнопка,
пагинация и последовательность вопросов также используют Flexbox либо обычный
поток. Вложенная Grid требует одновременно наблюдаемой строковой и колоночной
обязанности и подтверждается ревью.

Главная и категория показывают материалы одной вертикальной последовательностью.
Они не уплотняются в карточную сетку. Адаптивность меняет композицию по
смысловым состояниям оболочки, а не уменьшает настольную геометрию до
нечитаемого размера.

### ICW-CSS03. Скролл и ввод

Тематические скроллбары применяются ко всем прокручиваемым областям с
совместимым fallback. Скроллбар сохраняет достаточный контраст и видимый
ползунок.

Горизонтальное перетаскивание свёрнутой навигации использует Pointer Events,
захват указателя и порог намерения. Нажатие активирует ссылку до превышения
порога; после распознанного перетаскивания активация подавляется для текущего
жеста. Клавиатура, touch-scroll и колесо с поддержкой горизонтальной оси
сохраняют работоспособность.

### ICW-CSS04. Анимация

Анимация использует преимущественно `transform` и `opacity`, сохраняет
предсказуемую длительность и не блокирует управление. Содержательное состояние
доступно без завершения декоративной анимации.

Брендовый знак использует одно статическое состояние утверждённой IC-монограммы
с металлической поверхностью и красными сигнальными шевронами. Канонический
прозрачный raster master хранится в интерфейсной системе; один генератор создаёт
публичный SVG и квадратный favicon с безопасной подложкой. Независимые ручные
перерисовки и размерные варианты запрещены. Контекстный размер задаётся
параметром одного компонента и CSS.

`prefers-reduced-motion: reduce` отключает загрузочные, печатающие,
параллаксные и орбитальные эффекты либо заменяет их мгновенным состоянием.
Hover-эффект, несущий смысл, получает эквивалент `focus-visible`. Папка списка
материалов анимируется только при hover и доступном фокусе; статическая папка
внутри материала сохраняет спокойное состояние.

Печатающий эффект получает устойчивый идентификатор запуска. Повторный выбор
того же вопроса создаёт новый идентификатор, синхронно обнуляет видимую длину и
отменяет таймер прежнего запуска. Завершение проверяется только для текущего
идентификатора.

## 6. Качество программы

### ICW-L01. Линтинг и типы

ESLint использует flat config и типизированные правила Next/TypeScript.
Предупреждения CI запрещены. Неиспользуемые значения, необработанные Promise,
небезопасный `any`, нестрогое сравнение и беспричинное отключение правила
запрещены.

Внешнее значение проходит путь `unknown → validator → domain model`.
Закрытый union получает исчерпывающую обработку. Исключение преобразуется в
распознаваемую проектную ошибку на границе.

Stylelint проверяет CSS на синтаксические дефекты, неизвестные и повторные
свойства, конфликтующие декларации и выбранные стандарты. Prettier отвечает за
форму, Stylelint — за распознаваемые ограничения, человек — за архитектурную
уместность.

### ICW-L02. Публичные границы

Модуль предоставляет минимальную поверхность через именованные экспорты.
Default export используется в маршрутах и конфигурации, где его требует
фреймворк. Внутренний элемент не экспортируется ради удобства теста.

Client Component объявляется только при наличии состояния, эффекта или
браузерного API. Основное содержание, metadata и первый набор материалов
рендерятся на сервере.

### ICW-L03. Запрет разрозненного hardcode

Разрешённый hardcode ограничен неизменяемой семантикой компонента, стандартным
атрибутом и безопасным fallback. Следующие значения поступают из модели,
реестра семантического ядра, локали, material metadata либо build metadata:

- категории и элементы меню;
- пользовательские подписи;
- материалы и описания;
- подписи папок;
- независимые вопросы, ответы, graph views и навигационные подписи компаньона;
- связи переводов;
- SEO-метаданные;
- версия сборки;
- определения подсказок;
- пути брендовых ресурсов;
- подписи и состояние цветовой темы;
- подписи гимна, активная дорожка и её упорядоченные медиасточники;
- ID, DOI, название и PDF-файл связанной Zenodo-публикации;
- длительности загрузочной заслонки и скорость печати;
- системные пункты меню, их порядок, подписи, значки и состояния.

Fallback явно диагностируется и не маскирует отсутствие обязательных данных.

## 7. Проверки

### ICW-Q01. Типы проверки

Проект различает:

| Тип | Предмет |
| --- | --- |
| Модульная | Чистые правила каталога, локалей, подсказок и диалога |
| Контрактная | Соответствие адаптера порту |
| Интеграционная | Файлы содержания, маршруты, сборка и HTML |
| Архитектурная | Направления импортов и границы модулей |
| Негативная | Предсказуемый отказ без частичного результата |
| Визуальная | Сохранение утверждённой композиции и адаптивных состояний |
| Доступность | Семантика, клавиатура, фокус, контраст и reduced motion |

Тест использует публичную границу. Внутренняя последовательность фиксируется
только там, где она образует наблюдаемый контракт.

### ICW-Q02. Обязательные инварианты

Проверяются следующие инварианты:

- ID материала уникален;
- `translationKey` связывает не более одной редакции каждой локали;
- маршрут уникален внутри локали;
- опубликованный материал имеет обязательные непустые `description` и
  `memoryLine`;
- каждая альтернативная ссылка разрешается в существующую страницу;
- canonical указывает на текущую локализованную страницу;
- человекочитаемый индекс корпуса содержит все `published + public` страницы и сущности;
- `robots` разрешает публичное индексирование и объявляет существующий корневой
  sitemap index;
- четыре локализованные карты содержат по одной общей и одной вопросной карте
  для `uk` и `en`, а `sitemaps:check` обнаруживает drift без изменения файлов;
- каждый `published + public` вопрос имеет устойчивый маршрут, который
  раскрывает его в Индексе корпуса и перечисляет только канонически связанные
  материалы или страницы; другие виды индексных сущностей не получают
  параллельных сгенерированных маршрутов;
- навигационная категория разрешается в реестр;
- упразднённая категория `games` отсутствует в реестре и меню, её маршруты
  возвращают `404`, а API отклоняет фильтр `category=games`;
- подсказка разрешается в допустимый источник и безопасную форму;
- статически подготовленный диалог не содержит неизвестного вопроса или ответа;
- основной текст присутствует в серверном HTML;
- кнопка гимна присутствует в серверной оболочке после темы, а same-origin
  аудиоресурс имеет `preload=none` и запускается только клиентским действием;
- каждый материал явно объявляет возрастной рейтинг, а материал с предупреждением
  показывает доступное локальное подтверждение до чтения;
- сборка не изменяет канонические источники;
- импортные границы не образуют цикл;
- брендовый знак разрешается в один канонический ресурс;
- производные публичные SVG тождественны каноническому raster master по SHA-256;
- канонический master содержит одно состояние `ic-faceted-monogram-2026` без
  анимационных кадров;
- шапка, загрузочная заслонка и папка используют один параметризованный
  статический знак;
- квадратный favicon и публичный брендовый SVG воспроизводимо выводятся из
  одного master-файла;
- переход к компаньону скрыт только при одновременной видимости правой колонки;
- опубликованная Zenodo-связь разрешается в HTTPS-запись и объявленный PDF;
- категория в навигации ведёт на канонический адрес и возвращает
  отфильтрованный серверный HTML;
- устойчивый тег разрешается в двуязычный реестр, а один `tag` одинаково
  фильтрует серверную страницу, пагинацию и API;
- рёбра активного graph view заменяют предыдущий уровень вопросов внутри
  одного блока, сохраняя выбранный вопрос, путь и возврат; общий узел не
  копируется и цикл не создаёт бесконечный путь;
- сайт и Custom GPT имеют одинаковые `sourceCommit`, `contentVersion` и
  `contentDigest`, а `corpus:build:check` обнаруживает drift;
- публичная проекция содержит только `published + public` и не содержит
  `draft`, `review`, `deprecated`, внутренних заметок или закрытых сущностей;
- публичный индекс доступен на отдельной серверной странице, а выбор типа и поиск являются прогрессивным улучшением;
- публичные ссылки Zenodo используют постоянные concept DOI, а API/PDF сохраняют version-specific record ID;
- автор с URL отображается ссылкой, а structured data содержит его имя и URL;
- повторный запуск одного вопроса печатает полный ответ без дополнительного
  действия;
- однопредметные центрировщики не используют CSS Grid;
- тёмная и светлая темы сохраняют доступный контраст и одинаковый состав
  действий;
- первый загрузочный экран ждёт готовность и длится не менее 3 секунд при
  обычном движении;
- светлая и тёмная темы применяются к загрузочной заслонке до первого кадра;
- серверная пагинация, клиентский переход по номеру и прогрессивная подгрузка
  возвращают согласованные срезы;
- режим без JavaScript сохраняет навигационные ссылки и показывает только
  локализованное требование JavaScript вместо интерактивной панели компаньона;
- открытая подсказка имеет кнопку закрытия и остаётся открытой при нажатии вне
  своей области;
- `npm run check` оставляет рабочее дерево чистым;
- каждый зарегистрированный исторический тест присутствует, сохраняет
  удостоверенный SHA-256 и исполняется в объявленной фазе;
- production-сборка запускает `IRON WARDEN` до и после компиляции и прекращает
  выпуск при отказе любой фазы.

### ICW-Q03. Единая команда

`npm run check` является единственной полной не изменяющей источники командой.
Её этапы способны выполняться параллельно при одинаковом результате. Ошибка
возвращает ненулевой код и называет правило, файл, место и безопасное действие,
когда оно известно.

В состав команды входит `sitemaps:check`. Изменяющая команда
`sitemaps:build` запускается отдельно только при изменении опубликованных
маршрутов, вопросов, их связей, origin либо договора генерации.

Локальное автоматическое исправление предоставляется отдельной командой
`npm run format`. CI и checkpoint используют режим проверки.

### ICW-Q05. Экспериментальный контур IRON WARDEN

`/constitutional-guard/` является самостоятельным соседним проектом. Он
предоставляет собственную команду, манифест исторического корпуса и публичный
тестовый интерфейс. Построение теста вокруг приватной структуры приложения
запрещено; тестовый интерфейс наблюдает серверный HTML, HTTP-поведение,
канонические файлы и явно объявленные тестовые состояния.

Исторический тест получает устойчивый ID и остаётся действующим после
исправления исходной регрессии. Манифест фиксирует путь, фазу и SHA-256.
Runner сравнивает реестр с фактическим каталогом до запуска тестов. Отсутствие,
незарегистрированное добавление, изменение хеша, пропуск фазы либо падение
теста возвращает ненулевой код.

Прямое новое решение нормотворца способно заменить историческую норму, когда
новое обязательное поведение несовместимо с прежним наблюдаемым результатом.
Заменённый тест сохраняет файл и удостоверенный SHA-256, получает состояние
`superseded` и ссылку `supersededBy` на действующий зарегистрированный тест.
Runner проверяет целостность всего корпуса, исполняет только действующие нормы
и отклоняет замену без существующего активного преемника. Редактирование
содержимого исторического теста вместо этой процедуры запрещено.

Персонаж `IRON WARDEN` является интерфейсным выражением этого механизма на
уровне ядра. Его характер ограничен отказом и диагностикой. Он не меняет
источники, не формулирует нормы и не объявляет исключения. Результативность
эксперимента оценивается по предотвращённым регрессиям, стоимости сопровождения
и устойчивости тестового интерфейса.

Публичная исходная проекция включает полный исходный каталог WARDEN, режим
`integrity` и отдельные публичные prebuild/postbuild-фазы. Runner определяет
VOX по управляемому marker, всегда проверяет целостность всего исторического
корпуса и затем исполняет текущие тесты своей поверхности. Публичные фазы
проверяют запечатанную runtime-проекцию, build contract, локальные медиа,
лицензионную и секретную границу без доступа к закрытым редакционным источникам;
канонические фазы дополнительно исполняют действующие исторические нормы и
тесты полного дерева.

### ICW-Q04. Выпуск

Проверенный выпуск связывает полный Git SHA, lockfile, версии Node.js и npm,
редакции действующих актов, результаты проверок, активные исключения и
идентификатор публикации Sites.

Изменение кандидата прекращает действие прежнего результата. Успешная сборка
подтверждает техническую форму и не заменяет содержательное принятие.

Выпуск классифицирует изменение по матрице ICW-CL06, фиксирует версии записи,
материала, содержания, приложения, актов и схемы и применяет наивысшее
подходящее повышение по каждой оси. Выпуск также записывает результат проверки
Конституции и Законодательства, состояние IRON WARDEN, источник пересборки
проекций и состав публичного зеркала.

Публичная исходная проекция VOX собирается по исчерпывающему белому списку акта
`icw-act-vox-public-source-001`. Она содержит прикладной код, необходимые
публичные runtime-данные, безопасную build/test-конфигурацию, лицензионные
уведомления, принятый проектный нормативный контур, WARDEN и англоязычную
пояснительную документацию. Универсальная Конституция и исходная политика
лицензирования входят отдельными закреплёнными git-submodule. TheWorldOfCanon сохраняет отдельную архивную проекцию и
обновляется только при явно включённой архивной операции. Процедурные промпты,
attestations, внутренние отчёты, каноническая редакционная топология, секреты и
временные файлы исключаются из VOX.

## 8. Зависимости и исключения

### ICW-D01. Принятие зависимости

Прямая зависимость получает функцию, область, статус runtime или development,
лицензию, закреплённую версию, основание выбора и материальный риск.
Зависимость принимается при доказанном преимуществе перед небольшой локальной
реализацией.

Обновление React, Next, Vinext, Vite, TypeScript, парсера семантического ядра, sanitizer,
форматтера, линтера или генератора metadata получает отдельное рассмотрение,
поскольку способно изменить представление и доказательства.

### ICW-X01. Временное исключение

Исключение содержит устойчивый ID, правило, минимальную область, основание,
риск, компенсирующую проверку, владельца, срок и условие прекращения. CI
показывает состояние `waived` и отклоняет истёкшее исключение.

Исключение не способно отменить P12, обязательный внешний порядок, целостность
канонического источника и человеческое происхождение полномочия.

### ICW-X02. Локальное правило

Локальное правило возникает из повторяемого дефекта, принятого
архитектурного решения, ограничения технологии либо внешнего требования. Оно
получает источник намерения, область, обязательное поведение, способ проверки,
примеры соответствия и нарушения и отношение к настоящему акту.
